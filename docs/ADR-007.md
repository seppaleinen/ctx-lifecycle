# ADR-007: Global Pool LRU Eviction & Project Pool

**Date:** 2026-10-31
**Status:** Accepted
**Deciders:** Wayfinder Map #5

---

## Context

The original four-pool design (ADR-001) treated the Global pool as immutable — system invariants, types, and schemas that should never be evicted. In practice this caused unbounded growth: the Global pool accumulates across sessions with no state-transition eviction path, since it rides alongside every state rather than being swapped in and out like Planning, Execution, or Testing.

Two gaps emerged:

1. **No bound on Global pool size.** Without a cap, token usage grows without bound over multi-session lifetimes, undermining the flat-token-ceiling goal.
2. **No project-scoped scratch space.** Issue-specific notes, pinned requirements, and scratch work had nowhere to live that was both (a) available on every state and (b) cleared when a new issue starts.

## Decision

1. **Add a fifth pool: Project (`PoolID.PROJECT`).** It holds project-scoped context — issue notes, pinned requirements, scratch work — and rides alongside Global on every state via `getActivePools()`. It gets its own token ceiling via `pools.project.maxTokens`.

2. **LRU eviction for the Global pool.** Every time the `context` hook fires, the router calls `enforceCeiling(PoolID.GLOBAL, config.pools.global.maxTokens)`. Messages are evicted in ascending `accessedAt` order (least-recently-used first) until the pool is back under the ceiling. The same mechanism applies to the Project pool.

3. **`critical` flag for system invariants.** Messages flagged `critical: true` are skipped during LRU eviction — pinned requirements and system invariants survive trimming. If all messages in a pool are critical, eviction is a no-op (the pool stays over ceiling rather than dropping an invariant).

4. **Single global ceiling via `pools.global.maxTokens`.** No duplicate `globalMaxTokens` top-level key. The per-pool config object is the single source of truth; `DEFAULT_CONFIG.pools` enumerates every pool.

5. **Project pool cleared per-issue.** The `/new-issue` command calls `router.clearPool(PoolID.PROJECT)` to reset project-scoped context when starting a fresh issue.

6. **`POOL_KEYS` derived from `DEFAULT_CONFIG.pools`.** The `mergeConfig` function iterates `Object.keys(DEFAULT_CONFIG.pools)` to deep-merge user-supplied per-pool overrides. Adding a new pool requires only adding it to `DEFAULT_CONFIG.pools` — the merge loop, type interface, and router initialization all pick it up automatically, preventing config drift.

## Consequences

- **Positive:**
  - Global pool growth is bounded; token ceiling holds across sessions
  - Project-scoped context is available on every state and cleanly resettable
  - Pinned requirements survive LRU trimming via the `critical` flag
  - Adding a sixth pool is a one-line change to `DEFAULT_CONFIG.pools`
  - Single config source of truth — no duplicate ceiling keys

- **Negative:**
  - LRU eviction can drop useful Global context if the ceiling is set too low
  - `critical` flag adds a small per-message annotation burden for callers who want to pin content
  - Project pool adds a fifth in-memory structure (negligible; ~40 bytes per pool)
